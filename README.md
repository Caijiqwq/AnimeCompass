## 它解决什么问题

「今晚看什么」这件事，难的不是没得看，而是**选项太多而挑不出来**：排行榜前列的就那些，
视频站的推荐又总是那几部热门；想看点冷门的，又怕踩雷浪费一个周末。

这个站不做「猜你喜欢」那套。它只做一件事：**让评分与你的口味共同决定看哪一部**，并且把
「为什么推它」明说出来 —— 每条推荐都带一句人话理由，例如
「和《葬送的芙莉莲》一样有冒险、奇幻的味道，口碑站在第一梯队」。

## 三种用法

### 1. 照着最近看的推

输入 3–6 部刚看完 / 正在追的番（中文名、日文名、英文名都能搜），点一下按钮。

背后的做法：把这些作品的**类型标签、主题标签、制作公司、年代**展开成一个带权重的「口味画像」，
再和库里每一部作品算加权余弦相似度，叠加评分与热度做排序。
条目里几乎人人都有的背景标签（「男主角」「少年向」这类）会被排除，免得把相似度抹平。

同系列续作有特殊处理：整体降权（避免一上来就推第四季），但如果它的**前作正好在你选的作品里**，
则反过来加权 ——「看完第一季接着看第二季」是合理推荐，「直接推总集篇」不是。

### 2. 填一份口味问卷

不想一部部输作品的时候用。选类型标签、今晚的心情、年代、集数长度、最低评分。

「心情」的权重比类型更高：选「只想笑」会额外加权搞笑 / 无厘头 / 恶搞，同时压低恐怖与血腥；
选「治愈放松」则相反。这是为了让「我今晚想看点什么」这件事，压过「我平时爱看什么」。

如果条件太紧筛不出结果，会按 **形式 → 年代 → 集数 → 评分** 的顺序自动放宽，
并在页面上告诉你放宽了什么 —— 而不是甩一个空列表给你。

### 3. 随机一部优质番

实在没主意就用这个。从评分达标的作品里按**口碑的三次方**加权抽取：神作概率高，
但冷门高分作品依然有机会冒出来。只会抽到**系列起点**，不会第一次就抽到第三季。

## 功能

| | |
| --- | --- |
| 🎯 三条推荐路线 | 按最近看过 / 按口味问卷 / 随机优质（见上） |
| 🔍 搜索 | 中文名、日文原名、英文名都能搜；带别名（搜「情色漫画老师」能找到《埃罗芒阿老师》） |
| 🗂 全部番剧 | 按类型、年代、形式（TV / 剧场版）、最低评分筛选，按热度 / 评分 / 年份排序 |
| 📄 详情页 | 简介、标签、制作公司、评分、相似推荐 |
| ⭐ 双评分并列 | AniList 与 Bangumi 的评分同时显示，可切换「两边都显示 / 只看一边」 |
| 🈶 中文简介 | 优先用 Bangumi 官方简介，可切换中文 / English / 中英对照 |
| 📌 追番记录 | 收藏、标记看过，记录只存在你自己的浏览器里 |

## 界面与设计

配色是偏素的粉白：纸白底（`#fdfafb`）配一点浅粉强调色（`#d9738c`）。
没有渐变、没有玻璃拟态、没有满屏圆角卡片，界面里也没有一个 emoji ——
标题旁边是一支手绘风格的 SVG 小花，其余留给留白。响应式布局，手机单列，桌面最多七列。

## 本地运行

**注意：不要直接双击 `index.html`。** 浏览器的安全策略会拦截 `file://` 页面发出的 `fetch`
请求，页面会提示「数据集没能载入」。起一个静态服务器即可：

```bash
# 任选一种
python -m http.server 8000
npx serve .
```

然后打开 <http://127.0.0.1:8000>。

部署到 GitHub Pages 之后走的是 HTTP，没有这个限制，直接访问就能用。

## 部署到 GitHub Pages

站点全是静态文件、路径全是相对路径，**放仓库根目录或子目录都能跑**。

**做法 A：把这个仓库当作站点根目录（最简单）**

1. 仓库 **Settings → Pages** → Source 选 `Deploy from a branch`，分支 `main`、目录 `/ (root)`，保存；
2. 等 1–2 分钟，访问 `https://USER.github.io/REPO/`。

**做法 B：放到 `docs/` 目录**

把这个文件夹重命名为 `docs` 放进仓库，Pages 的目录选 `/docs`。

**想要 push 就自动发布？** 仓库里已经带了 `.github/workflows/deploy-pages.yml`：
到 **Settings → Pages → Source** 选 **GitHub Actions**，之后每次 push 到 `main` 都会自动部署。
另外也带了 `.nojekyll`，避免 GitHub Pages 用 Jekyll 处理静态文件。

## 目录结构

```
index.html            页面骨架
css/style.css         粉白配色与全部样式
js/recommend.js       推荐引擎（纯函数，浏览器与 Node 通用）
js/app.js             路由、三条路线的交互、浏览与详情
data/index.json       数据集元信息 + 分片清单（首屏读这个）
data/core.json        首发数据：800 部热门作品
data/part-*.json      其余 7 个分片
```

**数据是渐进加载的**：先加载 `core.json`，首页、随机、问卷立刻可用；
其余分片在 `requestIdleCallback` 里按顺序后台拉取，拉完一片就并进目录并就地刷新 ——
所以刚打开时搜冷门番可能还没有，过几秒再搜就有了。
浏览页会显示「完整目录还在后台加载：3/7 片」。全部加载完共 6175 部。

首屏只等 `index.json`（1 KB）+ `core.json`（约 1.4 MB，GitHub Pages 会自动 gzip 到约 680 KB）。

## 更新数据

数据是**构建时烘进这个文件夹的**，所以部署后不会自己更新。想刷新：

```bash
# 在完整版仓库（带 tools/ 抓取脚本的那个）里执行
node tools/build-data.mjs          # 重新生成数据集
node tools/build-deploy.mjs        # 重新打包静态版
```

然后把新的 `data/` 提交上来。

## 已知限制

- **没有服务端**：推荐全在浏览器里算，换设备不会同步收藏与记录；
- **中文简介覆盖 46%**：剩下多是冷门 OVA 与特别篇，切到中文时会照实说明并回落到英文原文，不假装有中文；
- **Bangumi 评分覆盖 44%**：没有 bgm 评分的条目只显示 AniList 分；
- 排序用的口碑值是 `AniList × 0.6 + Bangumi × 0.4` 再叠加热度与收藏数 ——
  一部作品到底值多少分本来就没有标准答案；
- 首次打开需要下载约 10 MB 数据（分片后台加载，不阻塞首屏）。

## 隐私

没有后端、没有埋点、没有第三方统计脚本、不请求任何 CDN。
收藏 / 看过的记录全部存在浏览器 `localStorage`（键名前缀 `rec.`），清掉浏览器数据就没了。
